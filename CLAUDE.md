# Japanese (personal learning app)

Personal, offline-only Japanese learning app for one Android phone. The full brief is in `prompt.md` and the approved plan is in the "Decisions" section below. Expo's own agent notes are imported here:

@AGENTS.md

## Commands

```bash
npm start                 # Expo dev server (open in Expo Go on Android)
npm run build:content     # download datasets + build assets/content-vN.db
npm test                  # Jest: app logic (src/**) and pipeline transforms (scripts/**)
npm run typecheck         # tsc --noEmit
npm run lint              # expo lint
npm run format            # prettier
npx expo install <pkg>    # always use this to add Expo/RN packages
```

A fresh clone must run `npm run build:content` once before `npm start`, because the content DB is gitignored.

## Structure

- `app/`: expo-router routes only (thin: each file renders one feature screen). We use root `app/`, not `src/app/`.
- `src/features/<feature>/`: everything one feature needs (`components/`, `hooks/`, `api/`, `types.ts`, `index.ts`). Other code imports only from a feature's `index.ts`.
- `src/shared/`: code used by 2+ features. It never imports from `features/`.
- `scripts/`: the Node data pipeline (`build-content.ts`, `sources.ts`, `steps/`, `lib/` = pure tested transforms).
- `data/`: hand-reviewed generated content (`components.json`, `mnemonics.json`).
- Import alias: `@/` = `src/`.

## Conventions

- TypeScript strict, function components, simple code with "why" comments (see the global CLAUDE.md).
- Styling: `StyleSheet.create` at the bottom of the file, colours from `useTheme()` (dark mode follows the phone).
- DB access: hand-written typed query functions in each feature's `api/` folder. No ORM.
- Tests: SRS logic and pipeline transforms only. No UI tests.
- Small commits per feature, each pushed to the private GitHub repo.

## Decisions

- **Two databases.** `progress.db` is created on the phone and is the main connection. The bundled content DB is copied from `assets/content-v{N}.db` and `ATTACH`ed as `content`, so one query can join progress with content. A content rebuild bumps `CONTENT_VERSION` and only ever replaces the content file. **Bump `CONTENT_VERSION` in `scripts/sources.ts` for every content change**, because the phone only re-copies when the file name changes. `src/shared/db/contentVersion.ts` and `contentAsset.ts` are generated by the pipeline. `ATTACH` is per connection, so queries that join `content.*` must not use `withExclusiveTransactionAsync`.
- **JLPT vocab tags** come from stephenmk/yomitan-jlpt-vocab (Waller's lists, keyed by JMdict seq id) because tanos.co.uk is offline. **Kanji JLPT** levels come from davidluzgouveia/kanji-data `jlpt_new`, because KANJIDIC2 only has the old 4-level field.
- **JMdict:** full `jmdict-eng`, keeping words that are common or JLPT-listed.
- **Pipeline:** builds the DB with Node's built-in `node:sqlite` (Node 24+), tokenizes with kuromoji directly (no kuroshiro), and unpacks archives with the system `tar`.
- **Component names:** Unicode Kangxi radical names where they exist, the rest in `data/components.json`.
- **Tatoeba** comes from the all-languages `sentences.tar.bz2`, because Windows `tar` can't unpack the bare per-language `.tsv.bz2` files. On Windows the pipeline calls `%SystemRoot%\System32\tar.exe`, since Git Bash's GNU tar misreads `F:` paths. The first download is about 370 MB and is cached in `scripts/.cache/`.
- **Frequency:** jmdict-simplified has no nfXX/ichi priority tags, so `freq_rank` = how many kept Tatoeba sentences contain the word, with common words winning ties. `study_order` = JLPT level (N5 first), then `freq_rank`.
- **Sentence cap:** at most 5 examples per word (`MAX_SENTENCES_PER_WORD` in `scripts/steps/sentences.ts`) keeps the DB at about 51 MB. A sentence is kept while any of its words still needs examples.
- **Study engine (`features/study`):**
  - **Items and cards:** an item is (item_type, item_key), and each card type gets its own FSRS card (`cardTypesFor`). The item types are kana, loanword, word, kanji and component.
  - **Building a session:** `prepareSession` picks due cards (most likely forgotten first, capped at `maxReviewsPerSession`) plus new items (`newItemLimit` halves them when the backlog is over the cap, and gives none above 3x). It introduces the new items up front.
  - **New-item order:** `study_queue` (words added by hand) first, then kana and words mixed by `mixCandidates`. Then `expandWithPrerequisites` puts each word's unlearned N5/N4 kanji, and their components, just before the word.
  - **Hiragana** turns a first Good into Easy, so it graduates fast.
  - FSRS uses ts-fsrs's legacy synchronous `fsrs()` API (FSRS-6).
- **Feature dependencies (no cycles):** study → kana, vocab, kanji, dictionary. vocab must not import study, which is why `markWordsKnown` lives in vocab. reading → dictionary. settings → study, reading.
- **Content data written by Claude:** `data/components.json` (component names; overrides Kangxi names) and `data/mnemonics.json` (245 N5/N4 kanji). The user edits mnemonics in the app (`mnemonic_edits`, never overwritten).
- **Backup:** Settings → Export/Import copies all 6 progress tables as JSON. Import replaces everything in one transaction. `BACKUP_COLUMNS` in `features/settings/lib/backupFormat.ts` must change with any progress migration.
- **Primary forms:** `words.kanji_text` / `kana_text` skip rare or irregular forms (sK/rK/iK/oK). All forms stay in `word_forms` for search. `glosses_fts` has one row per gloss, so group by `word_id`.
